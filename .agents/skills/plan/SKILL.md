# Plan

Скилл декомпозиции задачи на атомарные проверяемые шаги. Применяется **до** написания кода, обычно — сразу после `interview`.

## Когда применять

- Задача больше одного предложения и явно нетривиальна.
- Затрагивает ≥ 2 файлов или новую функциональную область.
- После `interview` получены ответы — пора превратить их в чек-лист.
- Пользователь явно просит план / декомпозицию.

## Когда НЕ применять

- 1 файл, 1 правка, поведение очевидно (тогда сразу код + `verify`).
- Исследовательский вопрос («изучи как работает X») — это `subagent(explore)`, а не план.

## Формат плана

### Масштаб задачи → формат

| Масштаб | Формат | Где живёт |
|---|---|---|
| 1 предложение, 1 файл | Без плана, прямое выполнение | чат |
| 2–4 файла, 2–5 шагов | Короткий нумерованный чек-лист в чате | чат |
| > 4 файлов / новая архитектура / новый раздел | Развёрнутый план + запись в `MEMORY.md` или `docs/adr/NNNN-...md` | чат + долговременная память |

## Структура каждого шага

Каждый шаг должен быть атомарным и проверяемым:

```markdown
- [ ] **Шаг N.** <что делается одной фразой>
  - Файлы: `<path1>`, `<path2>`
  - Проверка: <`npm run typecheck` | `npm test` | ручной визуальный чек | другое>
  - (опц.) Субагент: <`explore` | `general`>
```

- Одна правка = один шаг.
- Проверка после шага — конкретная команда, не абстрактное «потестить».
- Субагент — только если шаг изолирован (исследование) или делегируем (большая правка одного модуля).

## Когда НЕ раздувать план

- Шаги > 10 → пересмотри декомпозицию. Возможно, разбей на задачи (каждая задача = отдельный план).
- Шаги без проверки — у каждого шага должна быть проверка; иначе это не план, а wishlist.
- Зависимости между шагами — явно указывай в начале плана:

  ```markdown
  > Зависимости: шаги 2–4 параллельны после шага 1; шаги 5–6 — после 4.
  ```

## Связь с долговременной памятью

- Короткий план (5–7 шагов) остаётся в чате — этого хватает для текущей сессии.
- Развёрнутый план (≥ 10 шагов, новая архитектура) → записать в:
  - `MEMORY.md` секция «Что осталось» (если это часть roadmap)
  - `docs/adr/NNNN-<slug>.md` (если это архитектурное решение, см. `docs/adr/README.md`)

## Связанные скиллы

- **`interview`** — поставляет ответы, из которых строится план.
- **`verify`** — после каждого шага или в конце; не подменяет проверки самого плана.
- **`commit-push`** — после прохода `verify` коммитим и пушим.
