# Interview

Скилл «интервью вместо ТЗ»: прежде чем писать код, выяснить у пользователя ключевые неизвестные. Додумывать за пользователя запрещено.

## Когда применять

Задача подходит под **хотя бы один** из критериев:

- Формулировка в одном предложении, но подразумевает > 3 шагов или > 1 файла.
- Меняется публичный API, схема БД, маршрутизация, UI-компоненты верхнего уровня.
- Выбор между альтернативами (библиотека, паттерн, ORM, провайдер).
- Непонятно, что **не** делать (границы MVP).
- Непонятен критерий «готово» (что должно работать / появиться в UI/БД/логах).

## Когда НЕ применять

- Тривиальная правка: опечатка, переименование, форматирование, добавление одной строки в массив/список.
- Баг-фикс с чётким описанием и очевидным местом (например, «в логике X ошибка, исправь»).
- Рефакторинг в рамках существующих тестов — поведение не меняется, выбор стиля ясен.

## Алгоритм

1. **Прочитай контекст проекта** до первого вопроса — `AGENTS.md`, `MEMORY.md` (раздел «Что осталось»), релевантный раздел `docs/`. Это поможет задавать точечные вопросы, а не общие.
2. **Сформулируй 3–7 вопросов**, сгруппированных по темам. Используй `question(...)` для структурированных выборов или задавай в чате для открытых вопросов.
3. **Минимальный набор тем** (если релевантно — иначе оставь только нужное):
   - **Цель и не-цели** — что хотим получить и чего точно НЕ делаем (границы MVP).
   - **Пользователи / роли** — кто увидит результат (guest/host/admin), что конкретно появится в их UI/БД.
   - **Ограничения** — стек, перформанс, обратная совместимость, ограничения хостинга.
   - **Edge-cases** — пустые значения, ошибки сети, конкурентный доступ, таймзоны.
   - **Success-критерий** — какой прогон `npm run lint/typecheck/test/build` должен стать зелёным и что должно **физически** появиться (роут, файл, поле в форме, запись в БД).
4. **Жди ответа**. Не ускоряй: если пользователь ответил не на всё — переспроси только пропущенные пункты, не повторяй весь список.
5. **Сформулируй план** → подключи скилл `plan` (если задача больше тривиальной) → **только потом** пиши код.

## Чего НЕ делать

- Не задавать вопросы, ответ на которые очевиден из `AGENTS.md`/`docs/`/кода.
- Не задавать больше 7 вопросов за раз — пакетируй, если тем больше.
- Не переходить к коду, пока пользователь явно не подтвердил направление («ага, делай» / выбор варианта из `question(...)`).
- Не использовать `interview` как замену `verify`: интервью — про планирование, `verify` — про контроль.

## Связанные скиллы

- **`plan`** — после получения ответов превращает их в атомарный чек-лист.
- **`ponytail`** — перед добавлением новой зависимости/абстракции проверяет, нужна ли она вообще.
- **`tdd`** — для нетривиальной логики: сначала тест, потом код.
- **`verify`** — запуск проверок перед отметкой задачи как «готово».
