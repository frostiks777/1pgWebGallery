# ADR 0004: Агент в GitHub Actions: `/oc`, автотриаж, ревью, регулярный аудит

## Status

Accepted — 2026-10-13.

## Context

До этого репозиторий знал агента только в терминале: `interview → plan → verify → commit-push`
локально, задачи — в `ai/tasks/` и в GitHub Issues вручную. Разбор новой задачи, ревью PR и
регулярная проверка состояния проекта целиком зависели от того, что Андрей сидит за ноутбуком.

Набор воркфлоу взят из проекта-донора
[`ai-for-developers-project-387`](https://github.com/frostiks777/ai-for-developers-project-387)
(курс «ИИ для разработчиков», шаги 2–6): ручной вызов из комментария, автотриаж новых issue,
авторевью PR и регулярный аудит по расписанию. Механизм — GitHub App `opencode-agent`
(обмен OIDC-токена на токен приложения, `id-token: write`) и экшен
`anomalyco/opencode/github@latest`, модель `opencode/mimo-v2.6-flash-free` — та же бесплатная,
что в `opencode.jsonc`.

Что пришлось решить по месту, а не скопировать:

- **Аудит.** В доноре это Lighthouse по стенду на Render. Здесь единственный машинный сигнал о
  состоянии кода — вывод `eslint`/`tsc`, а прод — https://ap-p-g.duckdns.org/ с опциональным
  паролем на `WEBDAV_LOGON_PASSWORD` (замер может упереться в экран пароля). Решено: два
  независимых источника (проверки репозитория + Lighthouse по `APP_URL` из Variables), один
  разбор агентом.
- **Baseline.** На момент решения он пустой: `npx eslint .` и `npx tsc --noEmit` проходят
  чисто (ошибки `react-hooks/set-state-in-effect` и TS2345 в `video-stream/route.ts` починены
  коммитами `8a922af` и `4370e29`). Поэтому проверки в аудите не роняют прогон — их вывод всё
  равно уходит в отчёт и в разбор агента, — а промпт прямо говорит: любая ошибка линтера или
  типов это новая находка. Блокирующая проверка остаётся в `ci.yml`; дублировать её в аудите
  незачем.
  Отдельно в промпте оговорено, что не считать находкой два проектных ограничения:
  необходимость исходящего HTTPS к Google Fonts у `next build` и невозможность гонять e2e
  локально.
- **Деплой.** Пуш в `main` здесь означает rsync на прод (`deploy.yml`), в отличие от донора.
  Интерактивный воркфлоу оставлен с `contents: write` (иначе агент не сможет открыть PR по
  `/oc исправь`), а запрет пушить в `main` передан агенту текстом. **Этого недостаточно:**
  эндпоинту «Merge a pull request» по документации GitHub достаточно `contents: write`,
  то есть токен раннера в этом воркфлоу технически может слить PR через `gh pr merge`.
  Надёжная защита — branch protection на `main` («Require a pull request before merging»),
  и её нужно включить руками; до этого момента текстовый запрет — единственный барьер.
- **Триаж и ревью.** Промпты переписаны под этот репозиторий: реальные пути
  (`src/app/page.tsx`, `src/components/gallery/`, `src/proxy.ts`, `.data/`), реальные скиллы
  (`.agents/skills/interview`, `plan`) и реальные правила из `AGENTS.md` (русские строки, префикс
  `obs-`, `bunx`, Conventional Commits). В доноре промпт ссылался на скилл
  `plan-small-feature`, которого здесь нет.

## Decision

В `.github/workflows/` добавлены четыре воркфлоу:

| Файл | Событие | Права | Что делает |
|---|---|---|---|
| `opencode.yml` | `issue_comment`, `pull_request_review_comment` (`created`) | `contents/pull-requests/issues: write`, `id-token: write` | ручной вызов `/oc` или `/opencode` |
| `opencode-triage.yml` | `issues` (`opened`) | `contents: read`, `issues: write`, `id-token: write` | разбор новой задачи комментарием |
| `opencode-review.yml` | `pull_request` (`opened`/`synchronize`/`reopened`/`ready_for_review`) | `contents: read`, `pull-requests: write`, `id-token: write` | замечания к PR |
| `opencode-audit.yml` | `schedule` (`17 6 * * *`) + `workflow_dispatch` | `contents/pull-requests/issues: write`, `id-token: write` | `eslint`/`tsc` + Lighthouse → issue |

Общие решения по всем четырём:

- `id-token: write` везде, `share: false` явно (дефолт opencode для публичного репозитория —
  `share: true`, а в сессии видны вывод команд и код);
- фильтр событий от ботов (`sender.type`/`user.type != 'Bot'`), в интерактивном воркфлоу —
  ещё и `author_association` (владелец/участник/контрибьютор/контрибьютор);
- `timeout-minutes` 15–20 и `concurrency` с `cancel-in-progress`, чтобы агент не держал раннер
  до 360 минут и не наслаивал прогоны;
- `persist-credentials: false` везде, кроме интерактивного воркфлоу: там он нужен, иначе
  `git push` агента падает с «could not read Username»;
- модель `opencode/mimo-v2.6-flash-free`, ключ — в секрете `OPENCODE_API_KEY`;
- адрес стенда — в Variable `APP_URL`, не в файле.

`ci.yml` и `deploy.yml` не тронуты. Аудит не дублирует `ci.yml`: `ci.yml` блокирует сборку,
аудит — только заводит задачи.

## Consequences

(+) Разбор задачи, ревью PR и регулярная проверка перестали зависеть от того, что Андрей
за компьютером; следы работы видны в Actions и Issues.
(+) Аудит даёт регулярный машинный сигнал о коде: любая ошибка линтера или типов попадает
  в issue, а не теряется до следующего локального прогона.
(+) Адрес стенда в Variable — переезд прода не требует правки воркфлоу и коммита.
(+) `audit-report/`-артефакты (30 дней) + step summary дают историю замеров.
(−) Каждый вызов агента тратит минуты Actions и лимит бесплатной модели. Отсюда `timeout`,
`concurrency`, фильтр ботов, узкий круг вызывающих и «не больше двух issue за прогон».
(−) `/oc исправь` даёт агенту `contents: write` — единственное место в наборе, где агент может
коммитить. Защита от пуша в `main` текстовая, а не техническая: токен раннера не умеет merge,
но push в ветку `main` технически возможен, если промпт нарушит запрет.
(−) `opencode-review.yml` пропускает PR, открытые ботом. Следствие: PR от агента (бот) не
ревьюится автоматически — это осознанный размен минут Actions на отсутствие саморевью.
(−) Регулярный аудит добавляет до ~35 минут Actions в сутки.
(−) Расходы: у бесплатной модели есть дневной лимит запросов. Плановый аудит в 06:17 UTC может
исчерпать его и оставить ручные вызовы без ответа.

## Alternatives considered

- **Только `opencode.yml` (ручной вызов).** Дёшево по минутам Actions, но разбор задач и ревью
  остаются ручными — то есть ничего не меняется по сравнению с сегодня.
- **Аудит только по коду (без Lighthouse).** Отказ от замера прода: доступность и
  производительность в этом проекте не измеряются нигде, а именно на них жалуются гости.
- **Аудит только по Lighthouse.** Не ловит регрессии в коде — единственный машинный сигнал
  проекта (eslint/tsc) был бы не задействован.
- **Запуск `npm run test:e2e` в аудите.** Отклонено: в CI он требует Chromium и поднятого
  `next dev`. (Поправка 2026-10-15: в исходной формулировке отклонение опиралось на «e2e
  локально не гоняем» — это было неверно, тесты работоспособны, см. `checks.md`. Причина
  отклонения остаётся прежней: стоимость раннера, а не неработоспособность e2e. Пункт о
  возврате e2e в CI открыт в #13.)
- **Другая модель в воркфлоу.** Отклонено в пользу той же, что в `opencode.jsonc`, иначе
  агент в CI и агент в терминале будут вести себя по-разному.
