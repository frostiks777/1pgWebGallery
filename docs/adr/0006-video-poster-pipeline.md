# ADR-0006: Постер из видео — файл на диск, первый ключевой кадр ffmpeg

## Status

Proposed — 2026-10-16.

## Context

Прод лежал 11,5 часов (2026-10-15 23:23 → 2026-10-16 11:11) и выглядел мёртвым
для всех: TLS-handshake на `:443` не завершался, логи nginx не писались, sshd
не отвечал после KEXINIT.

Разбор (PR #53) вскрыл две независимые причины, обе в пайплайне извлечения
постера для видео без парной фотографии (`src/app/api/images/route.ts`,
`src/lib/ffmpeg.ts`):

1. **Память.** `fetchOriginal` вызывал `getFileContents(..., { format: 'binary' })`
   — весь клип материализовался в куче V8 (96 МБ у `C1145.MP4`, 134 МБ у
   `C1150.MP4`, до `VIDEO_PREVIEW_MAX_MB` = 300 по умолчанию) только ради одного
   кадра. Замерено на проде: RSS приложения растёт 183 МБ → 366 МБ за 110 секунд
   при простое, swap in/out 19–43 тыс. страниц/с, `vmstat` `id` 0%, `wa` 26%,
   `free` показывает available 36 МБ из 823.

2. **CPU.** `posterTimestamp()` возвращал 33% длительности, а `-ss` в потоке с
   GOP 250 заставляет ffmpeg **декодировать** все кадры от предыдущего
   ключевого кадра — около 230 кадров 4K HEVC Main10, чтобы дойти до 4,6 с.
   Замерено на проде: **11 582 мс** на один постер.

Отдельно уточнён механизм отказа: ядро писало
`TCP: out of memory -- consider tuning tcp_mem`, и nginx логировал
`upstream timed out (110)` на `GET /` от `127.0.0.1:3000`. То есть кончилась
не только RAM — кончилась память TCP-слоя. SYN/ACK и крошечные ответы (301,
400) проходили, а под handshake выделить память было уже негде. OOM-killer не
срабатывал ни разу: бокс не умирал, а **зависал** до ручной перезагрузки.

Усугубляло то, что `withFfmpegSlot` сериализовал **только шаг ffmpeg**, а
скачивание происходило **до** слота. Каждая запись очереди уже держала полный
файл в памяти, пока ждала.

Бокс: **1 ядро, 823 МБ RAM**, `worker_processes auto` → у nginx один воркер,
`nproc` = 1. Любая из этих двух причин поодиночке делает всю машину
неотзывчивой.

## Decision

1. **Видео стримится в scratch-файл, а не в Buffer.** Пик памяти процесса плоский.
   Скачивание перенесено **внутрь** `withFfmpegSlot`, так что на боксе единовременно
   существует ровно один исходный видеофайл.
2. **Постер — первый ключевой кадр** (`-ss 0 -skip_frame nokey`), а не 33% длительности.
   С откатом на обычный decode, если у потока нет keyframe-флагов.
3. **`-threads 1`** для ffmpeg. Одно ядро — пул потоков не даёт выигрыша и только
   конкурирует с единственным воркером nginx.
4. **Жёсткий SIGKILL-таймаут** на каждого потомка ffmpeg: зависший декодер больше не
   держит серверный слот навсегда.
5. **Пока постер генерируется, остальные получают `503` + `Retry-After`**, а не
   встают в неограниченную очередь.
6. **Масштабирование внутри ffmpeg** — sharp никогда не получает 4K-кадр.

Итоговый замер на проде, один кадр из `C1145.MP4`: **11 582 мс → 1 405 мс**.

## Consequences

**(+)** RAM приложения на этих операциях больше не растёт; CPU на постер упал ~8×;
один зависший ffmpeg не блокирует весь бокс; открытие видео перестало быть
способом уронить прод.

**(−)** Постер теперь всегда первый ключевой кадр. Прежний 33% выбирался специально
 («кадр 0 часто чёрный или логотип»), и в очень редких случаях кадр будет тёмным
или поймает переход. Это косметика на миниатюре 800 px — приемлемо, но это
осознанный размен.

**(−)** Видео всё равно качается целиком (96–134 МБ на диск, ~5,5 с). Убрать и это
не удалось — см. Alternatives.

**(−)** Второй запрос за то же видео по-прежнему идёт на постер и на `<video>`
одновременно: постер кэшируется в `.data`, так что платим мы один раз, но первое
открытие всё ещё тянет две операции.

**(−)** `VIDEO_PREVIEW_MAX_MB` теперь ощутимее как ограничение по времени скачивания
(не по памяти). Прод-митигация выставила 25 МБ, поэтому крупные видео временно
показывают заглушку.

## Alternatives considered

**Отдать ffmpeg URL WebDAV и дать ему ranged-чтение** — идеально, файл вообще не
качается. **Отвергнуто, проверено на проде:** ffmpeg 4.4 по протоколу http не
достаёт `moov` из хвоста файла. Файлы камеры (`ftyp XAVC`, Sony) не faststart.
Проверены варианты `-seekable 1`, уменьшенные `analyzeduration`/`probesize`,
без авторизации — во всех `moov atom not found`. Побочно подтвердилось: WebDAV
отдаёт `206` на `GET` с `Range` (в `HEAD` заголовка `Accept-Ranges` нет), то есть
идея верна технически, но **не для ffmpeg**. Nginx с этой задачей справляется —
см. #55.

**Просто снизить `VIDEO_PREVIEW_MAX_MB`.** Отвергнуто как единственная мера:
постера не будет вообще у всех видео, а дефект в 8× дорогого `-ss` останется.

**Оставить очередь, но ограничить её длиной.** Отвергнуто: пока запись ждёт в
очереди, она уже держит файл. Очередь была симптомом, а не причиной.

**`-ss` на 33% с `-skip_frame nokey`.** Отвергнуто: `-skip_frame` и seek плохо
уживаются — при недостижимой цели ffmpeg не находит ключевых кадров.

**Прогонять `ffmpeg -threads N > 1`.** Отвергнуто: `nproc` = 1.

**Перенести видео с Node на nginx.** Не отвергнуто, а вынесено в #55: это
убирает Node из потока байтов видео, но не чинит постер. Сделано отдельно, потому
что требует решений по хранению учётных данных WebDAV в nginx и по авторизации
маршрута (там своя дыра, см. #55).

**Ограничить память сервиса через `MemoryMax=`.** Не отвергнуто, но и не сделано:
это маскировка — процесс начнёт умирать вместо того, чтобы перестать есть память.
Прямое следствие инцидента: один Node-процесс унёс с собой nginx и sshd.

## Смежное, не закрыто здесь

- `net.ipv4.tcp_mem` стоит подобрать: ядро писало `TCP: out of memory`.
- `/api/images?path=` и `/api/video-stream?path=` отдают файлы без cookie даже при
  включённом `WEBDAV_LOGON_PASSWORD` (гейт на листинг работает: возвращает пустой
  список, а не 401). Зафиксировано в #55.
