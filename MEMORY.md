## Инцидент 2026-10-15/16: прод лежал 11,5 часа

Прод был мёртв с 2026-10-15 23:23 до 11:11 (10-16, ручной перезагруз). Симптом:
TLS-handshake не завершался, nginx и sshd не отвечали. OOM-killer не срабатывал ни
разу — бокс висел в зависании, а не умирал.

**Механизм отказа**: ядро писало `TCP: out of memory -- consider tuning tcp_mem`
(23:19:54), nginx — `upstream timed out (110)` на `GET /` от `127.0.0.1:3000`.
Память под handshake выделить было уже негде: SYN/ACK и крошечные ответы (301, 400)
проходили, а TLS-данные — нет. Триггером было открытие видео без парной фотографии:
пайплайн постера тянул весь клип (96–134 МБ) в кучу V8 ради одного кадра.

- **PR #53** (`fix/video-poster-pipeline`) — постер: видео стримится в scratch-файл,
  а не в буфер; постер — первый ключевой кадр (`-skip_frame nokey`), `-threads 1`,
  SIGKILL-таймаут, `503` вместо неограниченной очереди. Замер на проде:
  **11 582 мс → 1 405 мс**, RAM плоский. См. ADR-0006.
- **#55 (открыто)** — прокси видео nginx'ом напрямую (вынесено отдельно: это убирает Node из
  потока байтов видео, но не чинит постер; нужны решения по хранению учётных данных
  WebDAV в nginx и по авторизации маршрута).
- **PR #56 — смержен 2026-10-21** — #37: `cp -r public release/public` вкладывал `public/` в
  `release/public/public/`. Фикс в `main`, релиз 1.2.3.
- Митигация на проде: `VIDEO_PREVIEW_MAX_MB=25`, `NODE_OPTIONS=--max-old-space-size=512`.
- Не сделано: `net.ipv4.tcp_mem` не подобран.

**Ошибка, которую не надо повторять**: отдать ffmpeg URL WebDAV и не качать файл
нельзя. Идея верна (WebDAV отдаёт `206` на `Range` — проверено), но ffmpeg 4.4 не

**Начинать с [#52](https://github.com/frostiks777/1pgWebGallery/issues/52)** —
это критично: видео в галерее **не смотрится** в десктопном Chrome (HEVC Main 10
не декодируется, `videoWidth === 0`, звук идёт, картинка стоит), и пользователь не
получает никакой диагностики. Первое, что нужно сделать, — перепись кодеков по всем
169 видеофайлам (`ffprobe` через собственный прокси, не по прямому URL WebDAV),
чтобы понять, лечить один файл или делать транскод/детект массово.

**#52 и [#55](https://github.com/frostiks777/1pgWebGallery/issues/55), возможно, вместе**
— они про один и тот же маршрут `/api/video-stream`, и #55 всё равно переписывает его
целиком (nginx проксирует видео напрямую в WebDAV, Node уходит из пути байтов).
Пока `moov` лежит в хвосте файла, а `Range` на WebDAV работает, seek сохранится.
Но у #55 перед реализацией **два нерешённых вопроса**, и они не технические:

1. **Где в nginx живут учётные данные WebDAV.** nginx не читает `.env.local`;
   вариант — подстановка base64 из `.env.local` в `setup-nginx.sh` (секрет не уезжает
   в git) либо зашитый пароль в `nginx.conf` (против этого).
2. **Авторизация маршрута.** `WEBDAV_LOGON_PASSWORD` закрывает листинг, но **не**
   выдачу файлов: `/api/images` и `/api/video-stream` отдают байты без cookie
   (проверено снаружи 2026-10-15, в трекер не заведено). Если nginx пойдёт в WebDAV
   напрямую, проверка cookie на маршруте исчезнет совсем — дыру надо закрывать
   **вместе** с переносом, а не после. Порядок, который предлагает issue: сначала
   закрыть авторизацию файловых маршрутов, потом переносить видео на nginx.

**Но сначала — правки на сервере ради стабильности.** Переносить видео на nginx и
трогать маршрут на боксе, который недавно висел 11,5 часа, — риск повторить
инцидент. Сначала закрыть серверные задачи:

- [#60](https://github.com/frostiks777/1pgWebGallery/issues/60) — kernel-логи не
  переживают ребут (доказательства механизма отказа пропадают) + `net.ipv4.tcp_mem`
  не подобрана под 823 МБ;
- [#59](https://github.com/frostiks777/1pgWebGallery/issues/59) — `uncaughtException`
  «Invalid state: Controller is already closed» при обрыве клиентом не ловится,
  запрос уходит в никуда (не регрессия #53: первое вхождение 25 сентября).

Порядок: **серверная стабильность (#60, #59) → #52 (+ #55 вместе) → остальное**.

### Шаг 0 — разбить план на атомарные задачи (до первой правки кода)

Фаза или «скоуп» — это порядок, а не единица работы. До начала работ план режется на
атомарные issue: один issue = одно проверяемое изменение (одно поведение, одна фраза
«что меняется», одна проверка, которая может покраснеть). Один PR закрывает один issue
(`Closes #NN` в теле PR — GitHub закрывает issue при мержаже; `(#NN)` в коммите — только
перекрёстная ссылка, она ничего не закрывает). Если работа выросла за рамки issue — стоп и
новый issue, а не раздувание PR.

Причина записана в `AGENTS.md` и подтверждена историей: PR #53 привёз весь скоуп сразу,
два блокера прошли в `main`, и всплыли они только как #74 — после мержа. Фазы ниже —
очерёдность; конкретные работы создаются отдельными issue, когда до фазы доходит очередь.

Приоритеты и фазы остаются здесь как решение о порядке: что первым, что можно отложить
и почему.

### Ловушки, найденные при проверке плана (2026-10-20)

Три вещи делали бы работу «выполненной, но невидимой». Проверены по файлам, не по
описаниям.

1. **Кэш nginx обнуляет бамп версии на диске.** `nginx.conf:141-143`:
   `proxy_cache_key "$scheme$request_method$host$request_uri"`, `proxy_cache_valid 200 7d`.
   URL миниатюры (`PhotoCard.tsx:53`) версии не несёт, поэтому `-v3` в хеше `.thumbs`
   меняет только локальный файл, а nginx до 7 суток отдаёт старый WebP по тому же
   `request_uri`. **Решение: версия в URL (`&v=3`) + разовая чистка
   `/var/cache/nginx/images` при деплое.**
2. **Тот же ключ кэша обходит авторизацию (#72 → #91, закрыто).** Cookie в ключе нет, значит первый
   авторизованный `200` закэшируется на 7 дней и уйдёт анонимному клиенту. Дыру нельзя
   закрывать «просто проверкой в роуте»: в ключ попадает токен из `map $http_cookie`
   (не `$cookie_gallery_auth` — она ищет cookie `gallery_auth`), либо
   `auth_request` + `proxy_cache_bypass`, либо отказ от кэша `/api/images` при
   включённом пароле. `503` при этом не кэшируется (`proxy_cache_valid` задан только
   для `200`) — здесь конфиг корректен.
3. **Гейт линта на `main` нельзя терять.** #8 предлагает убрать `push: main` из
   `ci.yml`, но `deploy.yml:39-41` держит `bun run lint` с `continue-on-error: true`
   (комментарий там всё ещё про «9 pre-existing errors», хотя baseline 0). Прямой пуш
   в `main` деплоит прод, поэтому правки идут **парой**: снять `push: main` и сделать
   линт в `deploy.yml` блокирующим.

## API событий opencode v2 (проверено на v2.0.29 замером, не по памяти)

Дорого переоткрывается, поэтому фиксирую отдельно. Схемы: тег `v2.0.29`,
`packages/schema/src/{event,session-event,session-status-event,session-error,location}.ts`;
живой поток снимался временным пробник-плагином во время настоящего `opencode run`.

- Payload события — **`data`**, а не v1-`properties`: `{ id, created, type, durable, location?, data }`.
  Чтение `event.properties` даёт `undefined` (тихий отказ, а не ошибка).
- `session.error` в v2 **не существует**. Ошибка выполнения — `session.execution.failed`,
  текст в `data.error: SessionError.Error` = `{ type, message, status?, response? }`.
- `session.idle` живой, но помечен `// deprecated` (`session-status-event.ts`). Завершение —
  durable `session.execution.succeeded`; `session.execution.interrupted` несёт
  `data.reason: "user" | "shutdown" | "superseded" | "inactivity"` (на `user` уведомлять не надо —
  человек у клавиатуры).
- У `session.execution.*` **нет поля `location`** — только `{ sessionID }`. Поэтому чужие worktree
  отсекаются через `ctx.session.get({ sessionID })` → `Session.Info.location.directory` (с кэшем
  и TTL для отрицательных вердиктов). `session.created` несёт `location` в `data`, но только для
  сессий, родившихся после подписки плагина — долгоживущие так не поймать.
- Замер на этой машине: сессия сообщает **каталог worktree** (= `ctx.location.directory`), а
  `ctx.location.project.canonical` указывает на **главный checkout** (`C:\My_projects_GIT\1pg_gall`),
  то есть на соседний worktree. Сравнивать надо с `directory`, canonical в «свои» добавлять нельзя.
- Поток `/api/event` **volatile by contract** («a slow consumer overflows and fails the stream»),
  поэтому `await` в цикле `for await` допустим только для тех типов, которые плагин реально
  обрабатывает; остальное обязано отбрасываться без ожидания.
- Плагин грузится лениво и может догрузиться уже после рождения своей сессии — «неизвестная сессия»
  обязана пропускаться (fail-open), иначе уведомления замолчат совсем.

## Грабли, стоившие времени (2026-10-15)

- **fail2ban на sshd: `maxretry 5`, `bantime 10m`.** Бан выглядит как `Connection refused`
  (в jail REJECT, а не DROP), поэтому «порт упал» легко спутать с «sshd сломался». Признак:
  80/443 живы, а `/dev/tcp/<host>/22333` даёт RST. Правило: к прод-SSH — **одна попытка
  за раз**, без параллельного перебора user×key. Снять бан: `sudo fail2ban-client set
  sshd unbanip <IP>`.

- **PR-воркфлоу не запускаются, пока ветка конфликтует с `main`.** GitHub не создаёт merge ref,
  и на коммите оказывается **0 check-suites** — при этом `gh pr checks` пишет «no checks reported»,
  а не «конфликт». Симптом легко принять за задержку GitHub или поломку Actions (я так и сделал и
  потратил на это несколько проверок). Диагноз — `gh pr view <N> --json mergeable,mergeStateStatus`:
  `CONFLICTING`/`DIRTY`. Лечение — `git merge origin/main` в ветку и пуш.
- **`opencode-review.yml` (авторевью) идёт до 20 минут** и на мелких правках легко уходит в
  несколько раундов «мелочей». По этому плагину вышло 8 раундов: 4 находки были настоящими
  (пустой фильтр, врущий лог, слепой тест, недостижимая ветка таймаута), остальное — формулировки.
  Стоимость цикла стоит учитывать заранее.
- **Сборка может упасть на `NextFontGoogleFontFileReplacer`** (сетевой fetch Google Fonts на
  раннере) — это environment-dependent baseline из `AGENTS.md`, а не дефект дифа:
  `gh run rerun <id> --failed` обычно зеленит. Падает не только CI, но и шаг Build в
  `deploy.yml` (2026-10-26, деплой #107: `Can't resolve '@vercel/turbopack-next/internal/font/google/font'`)
  — тогда прод остаётся на предыдущей сборке, пока повтор не пройдёт. Сначала проверить, что
  диф не трогает `.ts(x)`/`next.config.ts`/`bun.lock`.
- **`npx` в этом репозитории не работает** (`EBADDEVENGINES`, #36): проверять только
  `bun run lint`, `bunx tsc --noEmit`, `bun run build`, `bun run test:e2e`,
  `bun run test:plugin-smoke`. Мои первые прогоны по этой задаче шли через `npx` на npm-дереве —
  то есть измеряли не то дерево, что CI и прод; пришлось перепроверять на `bun install --frozen-lockfile`.
